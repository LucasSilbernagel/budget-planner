# Database Migrations for Story 4-2

## Overview

This directory contains database migration scripts for Story 4-2: Create database schema for users table.

## Migration Files

### 0000_fix_users_id_type_to_uuid.sql
- **Purpose:** Convert users.id from serial (integer) to uuid
- **Type:** Breaking change migration
- **Status:** Manual migration script (not generated by Drizzle Kit)
- **Use Case:** Only needed if you have existing data with integer user IDs

## Background

### The Problem

During code review of Story 4-2, the Edge Case Hunter identified a **HIGH severity breaking change**:

The users table `id` field was changed from `serial` (auto-incrementing integer) to `uuid` with `defaultRandom()`. This is a breaking change because:

1. **Existing Data Incompatibility:** Any existing users with integer IDs cannot be referenced by the new uuid type
2. **Foreign Key Mismatch:** All financial tables (incomeSources, expenses, savingsGoals, balanceTracking, userProfiles) reference users.id, and they were updated from integer `userId` to uuid `userId`
3. **Migration Required:** If you have existing data, you must run a migration before deploying this schema change

### Current State

As of commit `94db5d2` (fix(db): address code review findings for story 4-2):
- ✅ `users.id` is now `uuid('id').primaryKey().defaultRandom()`
- ✅ All `userId` foreign keys are now `uuid('userId)`
- ✅ All foreign keys use `ON DELETE CASCADE`
- ✅ Email length is RFC 5321 compliant (254 chars)
- ✅ Timestamp mode fixed for JSON serialization

**Important:** If you have NOT yet created any database or populated any data, you do NOT need to run the migration. The schema is already correct.

## When Do You Need This Migration?

| Scenario | Need Migration? | Action |
|----------|----------------|--------|
| **New database, no data** | ❌ No | Just deploy the current schema |
| **Existing database with data** | ✅ Yes | Run `0000_fix_users_id_type_to_uuid.sql` |
| **Development database** | ⚠️ Maybe | Only if you have test data with integer IDs |

## How to Use

### Option 1: Automatic Migration Generation (Recommended for New Projects)

If you don't have existing data, just generate migrations normally:

```bash
# Set DATABASE_URL in .env
# Example: DATABASE_URL=postgresql://user:password@localhost:5432/budget_planner

# Generate migrations (creates files in packages/db/migrations/)
pnpm --filter db db:generate

# Apply migrations
pnpm --filter db db:migrate
```

This will create a clean migration that creates the users table with uuid from the start.

### Option 2: Manual Migration (For Existing Data)

If you have existing data with integer user IDs:

1. **Backup your database**
   ```bash
   pg_dump -U username -d budget_planner -F c -f backup_before_uuid_migration.dump
   ```

2. **Test the migration on a staging database first**

3. **Apply the migration**
   ```bash
   psql -U username -d budget_planner -f packages/db/migrations/0000_fix_users_id_type_to_uuid.sql
   ```

4. **Verify data integrity**
   ```bash
   # Check for orphaned records
   SELECT COUNT(*) FROM users WHERE id IS NULL;
   SELECT COUNT(*) FROM incomeSources WHERE userId NOT IN (SELECT id FROM users);
   ```

## Alternative: Safe Migration Script

For production environments with existing data, consider using a safer approach:

1. Create a new users_v2 table with uuid
2. Copy data with mapping
3. Rename tables atomically
4. Update application to use new table

## Migration Script Details

### 0000_fix_users_id_type_to_uuid.sql

This script performs the following operations:

1. **Add new_id column** to users table (UUID type)
2. **Populate new_id** with hash-based UUIDs derived from existing integer IDs
3. **Create temporary tables** for all financial data
4. **Copy data** to temporary tables with uuid references
5. **Drop old columns** and rename new ones
6. **Rename tables** back to original names
7. **Recreate foreign key constraints** with uuid type
8. **Verify data integrity** with validation queries
9. **Create indexes** for performance optimization

### Risk Mitigation

- **Atomic operations:** Uses PostgreSQL transaction-safe operations
- **Data preservation:** Copies all data before dropping old columns
- **Validation:** Includes verification queries at the end
- **Indexing:** Creates all necessary indexes for performance

### Limitations

- **Downtime required:** This migration requires database downtime
- **Not for hot migration:** Cannot be run on a live production system
- **Testing required:** Must be tested on staging before production

## Post-Migration Steps

After running the migration:

1. **Verify all tests pass**
   ```bash
   pnpm --filter db test
   ```

2. **Run linting**
   ```bash
   pnpm --filter db lint
   ```

3. **Update application**
   - Ensure all code references `users.id` as UUID type
   - Update any hardcoded integer ID references

## Rolling Back

If the migration fails:

1. **Restore from backup**
   ```bash
   pg_restore -U username -d budget_planner backup_before_uuid_migration.dump
   ```

2. **Revert to previous commit**
   ```bash
   git revert 94db5d2
   ```
